# prompt-editor —— 提示词编辑器（不负责绘图）

一个**纯编写**的 tab：把提示词按区块组织起来写，输出拼接后的纯文本，自己复制走。
它不连 ComfyUI、不提交作业、不出图 —— 与 `anima-example` 没有任何依赖关系；只有一条**单向**的跨插件调用（把输出发给 `anima-plus` 出图，D24，见下文「跨域调用」）。

```
┌────────────────────────────── 工作区 ──────────────────────────────┬────── 输出 ──────┐
│ ┌ 质量 ──────────────────────────┐ ┌ 主体 ────────────────────────┐ │ masterpice, ... │
│ │ [masterpiece] [best quality]   │ │ [1girl] [solo] [silver hair] │ │ 1girl, solo, ...│
│ └────────────────────────────────┘ └──────────────────────────────┘ │ 24 字符 · …     │
│                          [+ 新建区块]                                │ [复制]          │
└──────────────────────────────────────────────────────────────────────┴─────────────────┘
```

## 三个设计约定

1. **顶层结构只属于工作区。** 区块（边框 + 标题 + 颜色）是纯粹的视觉分组，不嵌套；
   最终输出是**拼接后的纯文本**，结构不进输出文本。保存预设时结构随 JSON 一起存 ——
   `doc`（区块/条目）是唯一真源，输出与草稿都是它的派生。
2. **tag 风格 / 自然语言是同一份内容的两种切分视图，开关挂在每个区块上。**
   - tag：按**括号深度 0 的逗号**切块（`(a, b:1.2)` 是一个块），输出时块内用 `, ` 串成一行；
   - 自然语言：按**英文句号**断句，句号留在前一句（只认「句号 + 空白/结尾」，
     所以 `1.5`、`v1.2` 不会被切开；`e.g.` 这类缩写会被当成句尾），输出时块内**每句一行**。
   - **没有全局开关**：每个区块表头各有一个 `tag | 自然语言` 小开关，块与块互不影响
     （质量块用 tag、场景块用自然语言是常态），输出时各块按自己的排版拼，块之间换行。
   - **tag 块末尾自动补英文逗号**：块是拿换行拼的，末尾没逗号的话，后面接的东西会跟最后一个 tag
     粘成一个（以前得自己在最后一个条目上补个逗号）。已经有逗号就不补第二个；自然语言块不补
     （句号就是它自己的结束符）。
   - **工作区的排版跟输出一致**：tag 块横着排成 tag 流，自然语言块**竖排、每句一行**
     （只改排版，不动数据 —— 一条一句仍然是各自独立的条目，译文格也跟着整行铺开）。
   - 换风格 = 把**整块当成一份内容**重切：按旧风格的连接符拼起来，再按新规则切。
     所以 `tag[masterpiece|best quality|8k]` 切到自然语言就是**一条** `masterpiece, best quality, 8k`，
     再切回 tag 又还原成那三条（拼接用的分隔符和切分规则是对偶的，往返可还原）。
     **块与块之间不合并** —— 块是工作区里唯一的结构。
   - 重建内容用的连接符（`CONTENT_SEPARATOR`）和输出的排版分隔符**不是一回事**：自然语言在输出里
     每句一行（`\n`），但拼回一份文本时句子之间必须是空格 —— 原文本本来就是空格分隔的，
     用 `\n` 拼会在切回 tag 时把换行带进 tag 里。
   - 两个例外，都是为了不静默改数据：**禁用的条目不参与合并、原样留在后面**（它本来就不进输出，
     并进去等于悄悄把它放回输出）；**译文清空**（译文对应整条文本，挂在碎片上是错的）；
     整块没内容（空块 / 全禁用）时原样不动。
3. **译文格已经在位、也能编辑持久化，只差数据源。** 每个条目下方那格（虚线小格）单击即可编辑，
   内容存进 `Item.translation`，跟着草稿与预设一起持久化；「译」按钮是下一步自动翻译的入口，
   接上数据源时不用改数据结构。

## 交互（对齐 WeiLin 的 tag 块）

| 操作 | 效果 |
|---|---|
| 单击块 | 就地改名；输入里带逗号（tag 风格）/句号（自然语言风格）会**按该块自己的风格重切**成多个块 |
| 双击块 | 启用 / 禁用（禁用只影响输出，不删内容） |
| 拖动块 | 块内排序；**块类型相同的两块之间也能拖**（tag ↔ tag / 自然语言 ↔ 自然语言）；拖区块表头左侧的 `⠿` 把手排序区块 |
| 区块表头的 `tag \| 自然语言` | 换**这个区块自己**的风格：整块当一份内容重切（别的块不受影响） |
| 「+」输入框 | **失焦即提交**（敲回车也行），不用记着按哪个键；一次粘一串按该块风格切分后逐个加入 |
| 区块表头的「存」 | 把这一块存进**区块库**（面板弹出来问名字，输入框自动抢焦点） |
| 区块色点 | 换颜色：8 个预设色，或**在色板里直接写一个颜色字符串**（`red` / `#f0f` / `rgb(…)` 都行；失焦或回车提交，值没变不写草稿） |
| 译文格（条目下方那个小格） | 单击就地编辑，失焦保存进 `item.translation`；「译」按钮是下一步自动翻译的入口 |

每个条目都是**上下两个小格**：上格原文（改名 / 禁用 / 拖动 / 删除），下格译文（虚线框，空的时候显示占位）。
译文只是写作时的参照，**永远不进输出**。

**区块颜色不限于预设色板**：色板里那个输入框收的是**任意 CSS 颜色值**（写错也不拦 —— 颜色只是个 CSS 值，
非法声明由浏览器丢掉，边框回到默认色、色点变成"没颜色"，比再给一套"为什么没生效"的提示划算）。
它和「+」输入框一个规矩：**失焦即提交**（回车也行），提交后**不关面板**（关掉的话输入框会随面板从 DOM 里
消失，"点别处 → 失焦 → 提交"这条链就断了）。

**跨块拖条目只认类型相同的块**（`canDropItem` / `moveItem`，见 `client/src/model.ts`）：条目是"按块自己的
规则切出来的碎片"，tag 的一条是逗号段、自然语言的一条是句子；跨类型搬过去，它立刻变成一条没有句号的
"句子"（反过来则会被逗号规则当成一个超长 tag）。两种切分视图之间**没有无损的单条映射**（要映射就得整块
重切，那是 `reflow` 的事），所以类型不同直接不接：光标变"禁止"、目标块不高亮、松手什么都不发生 ——
要换类型请整块换风格。落地时**源块和目标块各发一次条目写**（草稿是按组存的，不发源块它就还是旧顺序）。

### 提交输入必须读 DOM 的实时值（输入法的坑）

`v-model` 在**输入法组字期间不更新**（Vue 的 `vModelText` 里有 `if (e.target.composing) return`），
而中文输入法里"敲回车"往往就是**提交组字**那一下 —— `keydown` 早于 `compositionend`，
此刻 v-model 的 ref 还是空的。所以提交处理器一律读 `inputEl.value`（DOM 实时值）：

```ts
const parts = splitByMode(input?.value ?? adding.value, props.block.mode);
```

只读 ref 的话，中文输入法用户敲回车会被**整段吞掉**：字既没进工作区，输出自然是空的
（线上踩过，`scripts/interaction-test.ts` 里"输入法组字"那组断言专门锁这个）。
加条目 / 改名 / 改译文都是**失焦即提交**（`@blur`，回车也保留），所以"点走就算数"；
提交后还要显式清一次 `input.value` —— ref 没变过时 Vue 不会重渲染，DOM 里的字会留着。

## 数据落在哪

插件自己的空间（D12/D15）：`data/plugins/@comfyui-web+prompt-editor/`

| 文件 | 内容 |
|---|---|
| `presets.json` | 预设库（命名保存的**整份**结构），原子写 |
| `block-presets.json` | 区块库（命名保存的**单块**：标题 / 颜色 / 风格 / 条目文本），原子写 |
| `draft.json` | 当前草稿，**分两段存**：组结构 + 条目 |
| `tags.db` | 词库（**SQLite**）：**一张表两用** —— 翻译按 `en`/别名命中，面板按分类分组。`source:'user'` = 你改过的（导入不许覆盖它）· `import` = 外部机翻表导入的（见 [导入词库](#导入词库内置表--外部-csv)） |
| `settings.json` | 翻译设置：provider、自动译开关、每日上限、超时、两次调用最小间隔 |
| `usage.json` | 当日翻译调用次数（跨天自动清零） |

只有词库用 SQLite：它要装外部导入的十几万条；另外几个还是整文件 JSON（草稿上限 5000 条、
预设与区块库各上限 300 条，量级差着两个数量级）。为什么换、换到多少条划算、为什么不上 FTS5，
见 [词库往后怎么长](#词库往后怎么长) 的「规模」。

**内置机翻表不在上面这个目录里**：它是**产物里的资产** —— 源码
`plugins/prompt-editor/assets/danbooru-zh.csv`（**git-lfs**，5.2MB），构建时由 `pack.mjs` 的
extras 拷进 `tabs/prompt-editor/assets/`，服务端按 `import.meta.url` 读它来导入
（见 [导入词库](#导入词库内置表--外部-csv)）。

### 草稿为什么分两段

```json
{ "version": 1,
  "blocks": [ { "id": "b1", "title": "质量", "color": "#6ea8fe", "mode": "tag" } ],
  "items":  { "b1": [ { "id": "x1", "text": "masterpiece", "enabled": true, "translation": "" } ] } }
```

`blocks` 只放**属性**（顺序由数组本身表达），条目按区块 id 分到 `items` 里。于是编辑热路径上
**只有两个写事件**，各自只发"改了多大一块"：

| 事件 | 触发 | 请求 | 请求体大小 |
|---|---|---|---|
| 1. 组属性改变 | 区块增删 / 排序 / 标题 / 颜色 / 风格 | `PUT /draft/structure` | O(区块数)，**一个条目都不带** |
| 2. 某个组编辑完了 | 那个组的条目变了（增删 / 改名 / 禁用 / 排序 / 改译文） | `PUT /draft/blocks/:id/items` | O(该区块条目数) |
| （整份替换） | 载入预设 / 清空工作区 —— 不在热路径上 | `PUT /draft` | 整份 |

整份发的话，改一个字就要把全文档重新序列化 + 传一遍，放大太厉害；而且原来那套"深监听 doc +
防抖 700ms"在窗口里切 tab / 关页面会把最后一次改动丢掉 —— 现在失焦即写，没有待发队列。

两个实现细节：

- **删区块要清孤儿**：写结构时，结构里没有的区块，它的 `items` 一并删掉。
- **乱序兜底**：新建区块时"结构"和"条目"两次请求可能乱序到达，条目先到时给该区块垫一条默认属性
  —— 宁可多一个空区块，也不丢条目；下一次结构写入会按结构把它清掉。

接口（宿主统一加前缀 `/api/p/prompt-editor`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/presets` | 预设清单（只给摘要：名称 / 时间 / 区块数 / 条目数） |
| GET | `/presets/:id` | 取整份预设 |
| POST | `/presets` | 另存为新预设 `{ name, doc }` |
| PUT | `/presets/:id` | 改名 / 覆盖保存 `{ name?, doc? }` |
| DELETE | `/presets/:id` | 删除 |
| GET | `/draft` | 读当前草稿（两段装配成整份 Doc；盘上还是老格式也认） |
| PUT | `/draft/structure` | 写事件 1：`{ blocks: [{ id, title, color, mode }] }` |
| PUT | `/draft/blocks/:id/items` | 写事件 2：`{ items: [...] }` |
| PUT | `/draft` | 整份替换 `{ doc }` |
| GET | `/settings` | 读翻译设置 + 今日用量 + 词库条数 + provider 清单 |
| PUT | `/settings` | 写翻译设置（越界收敛到范围内） |
| POST | `/translate` | 翻译 `{ texts: [...] }`（1~50 条）→ `{ results: [...], error? }`，**按顺序对齐**。前端逐条发，这个接口本身也支持一批 |
| GET | `/tags` | 词库列表 `?q=&category=&limit=` → `{ tags, total, counts, categories }`（面板用） |
| PUT | `/tags/entry` | 写/改一条 `{ en, zh?, categories?, aliases?, source? }`；不给 `source` 沿用原值 |
| DELETE | `/tags/entry` | 删一条 `{ en }` |
| GET | `/block-presets` | 区块库清单（只给摘要 + 前 3 条预览） |
| GET | `/block-presets/:id` | 取整条（插入时才要） |
| POST | `/block-presets` | 存一块 `{ name, title, color, mode, items }` |
| PUT | `/block-presets/:id` | 改名 `{ name }`（内容不在这里改） |
| DELETE | `/block-presets/:id` | 删一条 |

服务端对进来的数据一律过收敛函数（形状 + 长度上限）：请求体和手改坏的 `presets.json` /
`draft.json` 都不该让页面炸掉（读坏了就退化成空文档）。

## 区块库：预设**单块**

跟预设库（整份文档）不是一回事：这里存的是**一块内容**，写提示词时看到某一块好用，存下来，
下次插到别的工作区里。入口是区块表头的「存」—— 点了把这一块的快照送到面板，面板问名字
（**输入框自动抢焦点**：不抢的话回车存不了、看着像没反应，分类改名那个 bug 就是这么来的）。

| | 存什么 | 不存什么 |
|---|---|---|
| 区块属性 | 标题 / 颜色 / 风格（`mode`） | —— |
| 条目 | **启用且非空**的条目文本 | 禁用的条目（它本来就不进输出，存进去再插出来等于悄悄把它放回输出）· 译文 · 条目 id |

- **不存译文**：译文对应的是当时的词库状态；插进来按**现在的**词库重新查才对（存旧的 = 悄悄给错答案）。
- **不存 id**：插入时现场生成（id 只要在本机文档内唯一）。
- **插入 = 新增一块、追加到最后**，不动任何已有区块。列表里只有摘要（条目可能几百条），
  插入时才按 id 取整条 —— 跟预设库同一套。
- 库上限 300 条；名字空白（只敲空格）算没名字，会被拒。

## 翻译怎么来的

固定 **英 → 中**。一条译文有四种来路，**优先级就是下面这个顺序**：

```
译文格 +「译」（单条 / 整块）+ 自动译
   │  POST /translate { texts: [一条] }        ← 前端逐条发，上一条回来才发下一条
   ▼
插件后端 server.js   ← provider 凭据只在这一侧，永远不下发到浏览器
   ① 词库命中 → 直接回（瞬时、零请求、零配额、没 key 也能用）
   ② 会话缓存命中（这次已经翻过同一个词）→ 直接回
   ③ 没命中 → provider 适配器去翻（串行 + 节流 + 撞限流退避重试）
   ▼
   结果**不写词库**：只挂在那一条条目上（跟着草稿落盘），标成「机」
   人认可它 → 手改译文，或点那个「机」→ 才进词库（`tags.db`）
```

**为什么 key 放后端**：这个部署是局域网 http（非安全上下文），浏览器直连要过各家 CORS、
key 还得进 localStorage；放后端顺带把缓存 / 限流 / 重试 / 换 provider 都收在一处。
`GET /settings` 只回 provider 清单和开关，凭据类字段一律不回传。

### 词库：一张表两用

落在 `tags.db`（SQLite，三张表）：

```sql
tags(key PK, en, zh, source, hot, updated_at, search)   -- search = 归一化正名 + 小写译文 + 别名，换行拼一列
tag_categories(tag_key, name)                            -- 一个 tag 可以属多个分类（"谁属于谁"）
categories(name PK)                                      -- 分类**本身**（含还没有词用的空分类）
tag_aliases(tag_key, alias_key, alias)
```

- **翻译**按 `key`（`en` 大小写/空白归一化）命中，`tag_aliases` 也命中（`cinematic light` → 正名）；
  别名撞上另一个正名时**以正名为准**。命中是一次主键查（14 万条实测 0.015ms/次），
  连接长持、语句预编译，所以"词库优先"仍然是零成本的那一步。
- **面板**按分类分组 + 搜索（英文/中文/别名都搜）+ 点击插入当前块。
  一个 tag 可以属多个分类（数组，不做单归属）；分类是**写作分类**（画质/光照/人物…）。
  Danbooru 官方那 5 类（general/artist/copyright/character/meta）不直接当分类名用 ——
  它会跟写作分类挤在一棵树上；导入时映射成 `机翻-通用/画师/作品/角色/元信息`，
  整组就是一个"待整理收件箱"（改完译文、换成自己的分类，它就离开这一组了）。
- 排序是 `updated_at DESC, hot DESC, key ASC`（索引 `idx_tags_rank`）：**你碰过的永远排在前面**
  （导入的行 `updated_at = 0`），同一批导入的内部按热度排。十几万条时那一页 300 条才是高频词，
  首屏（无搜索）也顺带成了"常用词" —— 所以导入敢全量：**噪声靠排序解决，不靠删数据**。
- 搜索是 `LIKE '%词%'` **全表扫**，不是 FTS5 —— 中文子串在 SQLite 自带的分词器里没有能用的那个：
  `unicode61` 把一整串中文当成一个 token（只有前缀命中）、`trigram` 只认 ≥3 个字符
  （`银发` / `电影` 这种两字查询直接返回空），而 node:sqlite **没有注册自定义分词器的入口**。
  14 万条实测：命中一堆的 0.5ms（列表凑够一页就收 + 总数封顶在 `limit+1`），
  **一条都不命中的 50~70ms**（一次完整全表扫，救不了 —— 给 `search` 建覆盖索引实测没用）。
  面板有 250ms 防抖 + 一次只回 300 条，够用（WeiLin 的 danbooru 库 14 万条也是这么扫的）。
- `source`：`user` 手动入库的（手改 / 显式存过）· `import` 导入的 · `builtin` 内置的。
  **面板里不按来源分标签**（进库就是库，一律标「库」），工作区的徽章也不看它（只看"在不在库里"）——
  这个字段现在只剩一个作用：**导入不许覆盖你手动改过的**（整条跳过，连分类/别名都不动）。
- 没有"按来源清空"这回事：进库的都是手动存过的，不想要就点「删」。
- **老文件自动迁移**：库是空的、且盘上还有 `tags.json`（或更老的 `dict.json`）时一次性搬进来，
  来源文件**改名成 `*.migrated`**（留个原件，同时免得你删了 `tags.db` 之后它又把那批老条目灌回来）；
  老 `dict.json` 的 `source:'api'`（机器现翻写进去的）归成 `import`。

两个入口（都在表头）：**词库…** = 管库 + 用库（搜索、改译文/分类/别名、删、插入当前块）；
译文格上的 **「机」** = 把这一条现翻结果存进库。插入会把**译文一起带进块**，所以插完不用再翻。
在面板里**动过就升成 `user`**（改译文、改分类、改别名都算：导入的十几万条里，你把某条从
「机翻-角色」挪进自己的分类，下次导入不许把它冲回去）。
在工作区点「机」= 把这份现翻的**存进库**，标记跟着从「机」变「库」（进库了就不再是"现翻的"）。

### 编辑模式：插入与编辑互斥

面板顶部一个开关，**插入和编辑二选一**（默认关）：

| | 关着（浏览，默认） | 开着（编辑） |
|---|---|---|
| 行上 | **只有「插入」** | **「改 / 删」**（「插入」藏起来） |
| 分类标签上的摘分类 `×` | 不出现 | 出现 |
| 左边分类树 | 纯筛选 + 拖拽落点，**没有任何管理入口** | 顶部「＋ 新建分类」+ 每行「改 / 删」 |
| 开关自己 | 普通 | **变蓝**，一眼看出"现在能删东西" |

为什么互斥：「**删**」没有二次确认（直接把这条从库里删掉），而它原来就挨着「插入」—— 想插一条手抖点偏一格，这条就没了。
插入是日常动作、编辑是"我要动手整理"，两件事不该出现在同一个位置。

**每次打开面板都回到浏览模式**（编辑模式不粘着）：开着的时候「插入」是藏起来的，粘着它会让面板一打开就没有主操作。
关掉开关 / 重开面板时，会把这一层里所有"编辑中的半成品"一起收掉（行内表单、分类树上的新建/改名/删除确认），
免得出现"模式关了、某一行却还是表单"这种自相矛盾的状态。

**拖拽不受这个开关管**：排序和拖到分类上照样随时可用 —— 拖是有意图的动作，不会误触，
而它正是整理这十几万条的主力。

### 拖拽：排序 + 改分类

每行最前面有个**六点手柄**（内联 SVG，不是图标库）告诉人"这行能拖"；行本身也能拖，手柄只是把这件事说出来。
一拿起手柄，**左边整列点亮**（所有能放的地方都显出来），悬停到的那个再加强 —— 光高亮悬停的那个不够，
人得先知道有哪几个地方能放。

| 想干什么 | 怎么操作 |
|---|---|
| **排序** | 拖到两行之间（行上/下半边决定插到它前面还是后面），松手即写 |
| **换成另一个分类** | 拖到左边某个分类上 |
| **去掉分类** | 拖到左边「未分类」（那是个真状态，不是特例）；或点行上分类标签的 **`×`**（要先开编辑模式） |
| **加/减、一次改好几条** | 先开编辑模式，再点「改」进编辑态：**点分类标签 = 加/减**（选中的高亮），输入框仍在（批量改、**造一个全新的分类名**） |
| **新建/改名/删除分类本身** | 先开编辑模式，左边分类树（顶部 `＋ 新建分类` / 每行右侧 `改` `删`；见下面的[分类级管理](#分类级管理新建--改名--删除)）—— 上面几条改的都是"某条词属于谁"，这条改的是分类自己 |
| **调整分类的顺序** | 拖左边分类行（每行最前面也有六点手柄）：落点在某一行的上/下半边 = 插到它前面/后面 |
| **批量删除某个分类下的词条** | 先开编辑模式，点该行的 **`清`** → 确认（那些词条**从库里删掉**，分类留着）—— 面板上唯一的批量删除入口 |

**一个 tag 只属于一个分类**（实测库里 134346 行全是单分类），所以拖到分类那条路**只发一个分类**
（`categories: [name]`）—— 是"换成它"而不是"加一个"。它和另外两条增减路走的是同一条写入
（`PUT /tags/entry` 带 `source:'user'`），所以拖完的分类**重导机翻表不会被冲回去**。

**排序只在「全部」且没搜索时可用**：顺序是相对"一整页"说的 —— 面板把这一页的新顺序（`keys`）和
**被拖的那一条**（`moved`）发给 `PUT /tags/order`。**有 `sort` 的排在最前，其余仍按热度**。筛选 / 搜索
出来的是一小撮，在那一小撮里拖一下就会把它们整批顶到全库最前面，那不是"我在结果里挪了一下"，
所以筛选态下不接排序（拖到左边换分类照旧）。

`sort` 是 **REAL**，铺序号时按 `index * 1000` 留间隔，拖一下**只写被拖的那一行**（取左右邻居的中点）。
两种情况下退回"整页重铺间隔"（响应里 `rebuilt: true`，面板提示会写「重排了序号」）：
这一页有行还没铺过序号（第一次拖，或刚"加载更多"带进来一批），以及浮点切尽
（同一个缝里对半切 ~50 次就切不出严格居中的值了）。**页面 = 全库的前缀**（排序只在无筛选时可用），
所以"页顶"就是"全库最前"，顶 / 底那侧没有邻居时留一个间隔的余量就够。

`sort` 是后加的列，老库开库时自动补；类型不对（早先落过 `INTEGER`）会重建这一列
（`DROP INDEX` → 抄下已排的值 → `DROP COLUMN` → `ADD COLUMN sort REAL` → 写回，全在一个事务里）。
排序索引 `idx_tags_rank2` 是**必须的**：`ORDER BY (sort IS NULL), sort, updated_at DESC, hot DESC, key`
跟老索引对不上，没有它就是"全表扫 + 临时 B 树排序"—— 14 万条实测 **0.2ms → 22.9ms**。
`setOrder` **不动 `updated_at` / `source`**：排序是"我怎么摆这一页"，不是"我改了这条的内容"。

**加载更多**：面板一次取 300 条（`limit` 从 300 起，每次 +300，服务端夹到 1000），列表底部按需出现
「加载更多（已显示 N）」。头部那行字**筛选时显示命中数**（`命中 257 条 · 全库 134353`）——
命中数被 `limit + 1` 截断时只能写 `N+`（精确值要全表再扫一遍，22ms，是当初故意不做成精确的）。

**分类自己是一张表**（`categories`），不只是 tag 上的字符串 —— 所以**空分类也能存在**，
"先建分类、再往里放词"走得通。计数不存两份（存了就要同步，同步一定会漂），
开面板时从 `tag_categories` 现算；并列时按**码点序**（SQLite 的 `name ASC` 是 BINARY 排序，不是拼音）。
老库不用手工迁移：开库时 `INSERT OR IGNORE ... SELECT name FROM tag_categories` 把在用的名字补进来，
写词时填的新名字也顺手注册（见 `writeEntry`）。

#### 分类级管理（新建 / 改名 / 删除）

> 这一整节的操作都要**先开编辑模式**（见上面的[编辑模式](#编辑模式插入与编辑互斥)）—— 浏览模式下分类树只是个筛选器。

**`清`（批量删词条）≠ `删`（删分类）**，两个都要确认，但结果完全不同：

| | 归属（哪些词属于它） | 分类本身 | 词条 |
|---|---|---|---|
| **清** | 一起删 | **留着**（变成一个计数 0 的空分类） | **从库里删掉**（不可撤销） |
| **删** | 一起删 | 一起删掉 | 一条不删，只是变回未分类 |

`清` 是面板上**唯一的批量删除入口**（逐条删要点 N 次「删」）。手改过的（`source = 'user'`）**一样删** ——
这是"我明确要删这一批"，不是导入那种"别覆盖我的"；返回值里带上其中几条是手改的，面板会写进提示
（删掉的东西不可撤销，至少要让人知道自己删掉了什么）。实测删 46075 条 809ms。

**分类顺序**存在 `categories.sort`（`REAL`，跟 tag 的 `sort` 同一套浮点中点法）。区别是**第一次拖就整树铺序号**：
分类只有几个到几十个，一次全写也就几行，铺完顺序就是"你拖出来的那个顺序"，不会出现"拖了一条、它跳到最前、
其余按计数排"这种半手动状态（十几万条的 tags 做不到，所以那边是"手动的是前缀"）。新建的分类没有序号，
排在最后；拖它时整树重铺。

> **坑（实测挂住过）**：分类树的计数查询必须**先去重再 JOIN**。`tag_categories` 里每个 `(tag_key, name)` 都有一行，
> 直接拿它 JOIN 自己就是"组内每条乘组内每条"—— `机翻-画师` 那 46075 条的组会算出 21 亿行，面板直接卡死。
> 所以里层先按名字收敛成一行（`MAX(sort)`：同名两处都有时以 `categories` 那份为准），外层再 JOIN 数个数。
> 小样本上的表现是**计数翻倍**（4 条词的分类会显示 16），contract-test 里就钉着这条。

分类树顶部就是这批操作（`＋ 新建分类` / 每个分类行右侧的 `改` / `删`）：

| 操作 | 在哪 | 注意 |
|---|---|---|
| **新建** | 左边顶部「＋ 新建分类」 | 只加名字，**一条词都不动**；重名不当错误（提示"已经有一个同名的了"） |
| **改名** | 分类行右侧的 `改` → 顶部出输入框 | 输入框**自己抢焦点**（不抢的话 `enter`/`esc` 永远不触发，看起来就是"点了没反应"），另有「改名 / 取消」两个按钮；`categories` + `tag_categories` 两张表一起改；**撞名不合并**（409），合并不可逆而打错字重打一次就行 |
| **删除** | 分类行右侧的 `删` | **连它下面的归属一起删**，所以先摆出"影响 N 条"再确认；`tags` 一条都不删，那些词只是变回未分类 |

拖拽的落点仍然只存在于树里 —— 但树现在包含空分类，所以**新建完就能往里拖**。
再导入机翻表会把 `机翻-*` 那些名字重新带回来（导入自带分类），这是预期。

### 导入词库（内置表 / 外部 CSV）

**面板按钮**：词库为空时，面板里直接给一条路 —— 不用自己去收集 CSV：

> 也可以先导入内置的 danbooru 机翻表（5.2MB，约 14 万条）…　[导入内置机翻表]

点一下就把**产物自带**的那份 CSV 灌进 `tags.db`（14 万行实测 2.1s，分批写、块间让出事件循环，
不把宿主卡住）。库里有东西之后这个按钮挪到面板页脚（「重导内置机翻表」）—— 换了新版 CSV 再导一遍用。
**不会自动导**：写几十 MB 是显式动作。

那份 CSV 是 `plugins/prompt-editor/assets/danbooru-zh.csv`（**走 git-lfs**，5.2MB），构建时由
`pack.mjs` 的 extras 拷进 `tabs/prompt-editor/assets/`，于是：

- 服务端按 `import.meta.url` **直接读自己目录里的它**，不走浏览器上传 —— 14 万行没必要过一遍
  HTTP 和宿主内存，解析规则也就能和命令行共用一份（`server/tagcsv.ts`）；
- `dist/` 整包搬走也带着它：**LFS 只在源码 checkout 那一侧存在**，部署机不用装 lfs；
- 但 clone 时没装 lfs（或 `GIT_LFS_SKIP_SMUDGE=1`）时，源码里躺着的是 130 字节的**指针文件**。
  这条路被显式挡住：读到指针就报「先 `git lfs pull`」，而不是"导入成功，入库 0 条"。

**命令行（任意 CSV）**：

```bash
pnpm -C plugins/prompt-editor import:tags ~/danbooru-zh.csv                       # 全量
pnpm -C plugins/prompt-editor import:tags ~/danbooru-zh.csv -- --min-count 100    # 只留 count>100
pnpm -C plugins/prompt-editor import:tags ~/danbooru-zh.csv -- --dry-run          # 只看统计，不写库
```

列序 `tag,category,count,译文`（按表头名字认；表头写 `alias` 也当译文读 —— 这份表是机翻表）：

| 列 | 去处 |
|---|---|
| `tag` | 正名（`key` 按 `tagKey` 归一；同键去重时留 count 大的那条） |
| `category` | 数字 → `机翻-通用 / 画师 / 作品 / 角色 / 元信息`（0/1/3/4/5）。**6 是源表自己的兜底桶**（身体部位、组合词、个别作品混在一起），归「机翻-其他」；认不出的数字同样归「其他」，空值 = 未分类 |
| `count` | `hot`（面板排序用；也留着以后按热度砍档） |
| 第 4 列 | `zh`。**空译文的行跳过**，**译文和正名一样的行也跳过**（后者是机翻表里没翻出来的占位，真表里 8224 行 / 5.8%）—— 命中一条没译文的词等于白占一次「库」命中，不如让接口去翻 |

真表里有**引号包着的字段**（48 处），而且引号里带逗号：`"my_hero_academia,",6,39259,我的英雄学院`、
`otu_(o2h2_oh4),1,679,"otu (O2H2, Oh4)"` —— 解析按 CSV 规矩读，不是按逗号裸切。

三条要点：

- **不覆盖你改过的**（`source='user'` 整条跳过，连分类/别名都不动），所以换 `--min-count` 重导
  几次都不会把整理好的那批打回原形。
- 导入的行 `updated_at = 0`：面板排序是 `updated_at DESC, hot DESC`，于是"你碰过的"永远压在
  "一整批导入的"前面，导入那批内部按热度排。
- **不用重启宿主**：两条路写的是同一个 `tags.db`（WAL 允许宿主同时读），宿主的计数缓存靠
  `PRAGMA data_version` 自己发现外部写入（它只在**别的连接**提交后才变）。

### 词库只装"人认可的"（导入的机翻表另算）

译文格右下角有个来源标记，一眼能看出这条**要不要再问接口**：

标记只说一件事：**这条译文在不在词库里** —— 在库里 = 以后零请求，不在 = 每次都得问接口。

| 标记 | 含义 |
|---|---|
| **库** | 在库里，而且是**人写的**：你手改/手填的、点「机」存过的、内置词表 |
| **导** | 在库里，但来自**导入的机翻表**（`source:'import'`）—— 零请求，只是没人校对过 |
| **机** | 机器现翻的，**还没进库** —— 点一下把这份译文存进词库（标就变「库」），下次别的块遇到同一个词零请求 |

没有标记 = 这条没有译文（或老预设里来路不明的译文）。这是**工作区**里的标记；
词库面板里不按来源分标签（进库就是库，一律标「库」）。

**导入十几万条之后，大部分词会是「导」而不是「库」** —— 一眼就能看出"这条我没动过"。
要改就去**词库面板**（`机翻-*` 那几个分类就是还没整理过的），改完它就从「导」变「库」，
以后导入再也动不了它。想整批清掉：`DELETE FROM tags WHERE source='import'`，或按 `hot` 筛。

为什么不让**现翻结果自动进库**：词库是"我认可的词表"，混进机器翻的就分不出哪些能信了 ——
导入是你显式选的一次性动作（标「导」就是它的"来路"），现翻结果自动入库则是静默的，性质不一样。
代价是同一个词换个块还要再翻一次 —— 所以进程内还有一个**会话缓存**（重挂即清，不落盘），
同一个词一个会话只问一次。

### 逐条发 + 限流

有道体验版**限流很紧**，实测（`aidemo.youdao.com`，HTTP 一直是 200，限流藏在 body 里）：

| 间隔 | 结果 |
|---|---|
| 连打 | 第 7 次开始 `{"errorCode":411,"msg":"请求频率过快"}` |
| 1.5s | 第 6 次开始 411 |
| **6s** | **连打 8 次全过** |
| 触发后 | 8s 未恢复；几分钟后恢复 |

所以：

- **前端逐条发**：一次只发一条，上一条回来才发下一条。打包成一批只会让一个 HTTP 请求挂很久
  （节流 6s × 10 条 = 1 分钟），而且中途失败会连坐整批。
- **服务端全局节流**（`minIntervalMs`，默认 6000）：记的是"上一次真的打出去"，**跨请求、跨批次都算**
  —— 换个批次、换次点击也照样等。
- **撞上 411 就退避重试**（20s、40s，最多 2 次）：偶尔限流不该让整批红掉。重试用尽才标失败，
  错误码是 `RATE_LIMIT`。

### 四条硬规则（都是"不静默改数据"）

1. **手改的译文写回词库且永不被覆盖**（`source:'user'`）：改过一次，以后自动命中它。
2. **自动译不覆盖任何已有译文**：队列只收"还没有译文"的条目；整块「译」也只翻没有译文的那些
   （要重翻某一条就点它自己的「译」）。
3. **改名清掉旧译文**：译文对应的是**整条**文本，改了文本它就对不上了；而且"有译文就不再自动译"
   会让这个错误一直留着。所以改名时清空译文（自动译随后补上正确的），但**往一条后面追加**
   （第一段文本没变，`a` → `a, b`）时保留 —— 那一段的译文还是对的。
4. **权重语法不许翻坏**：`maskPromptSyntax()` 先把要翻的词剥出来，翻完按原样贴回 ——
   `(masterpiece:1.2)` → `(杰作:1.2)`、`{a|b}` 每支各翻、`<lora:...>` 直接跳过
   （模型名是标识符，翻了就废）。认不出来就整条当普通文本翻。

自动译的隐式调用是被管住的：条目**失焦提交**后攒 400ms 合成一个队列（连着敲几条只排空一次），
然后**逐条**发；配额按**整条文本**算（宁可少翻几条，也不把 `{a|b}` 翻一半）；`maxCallsPerDay` 是护栏，
烧光了自动译停下、格子上留个红框记号，不弹窗、不阻塞写作。失败同理：条目本身照常落盘。

翻译回来的译文也算"这个组编辑完了"，会触发一次该组的条目写入（按组去重，一组一次）——
不然刷新一下刚翻的译文就没了。

## 跨域调用（输出 → anima-plus）

输出区下面挂着一个跨域调用区：**把这份输出当作 anima-plus 的描述提示词，直接向它发起一次出图**。
这是本插件唯一一条跨插件依赖（D24，`docs/architecture.md` §2/§14.6），方向单向 —— anima-plus 不知道这边存在。

- **参数基底 = 对方的「最后一次状态」**（`data/plugins/<包名>/last-state.json`）：只有 `prompt` 被换成这里的输出，
  模型 / 尺寸 / 步数 / LoRA 全都沿用你上次在 anima-plus 那边跑过的那一套，面板上会列出摘要。
  对方**没跑过一次**就没有基底 —— 这时按钮是禁用的，并写明原因（不猜模板默认值）。
- **随机种子**：对方快照里 `randomSeed` 为真时，这次提交会**重抽一个种子**（与它点「开始生成」同一套行为），
  回执里报出抽到的数；为假时沿用快照里的种子。
- **提交两件事**：先 `PUT /api/p/anima-plus/api/state` 把这份值写回对方快照（这样你切过去看到的参数就是这次的），
  再 `POST /api/p/anima-plus/api/jobs` 建作业。回执给 jobId / 排队位，以及一个去 `/w/anima-plus` 看进度的链接。
- **预热**：探测到对方可用就顺手 `GET /api/p/anima-plus/api/deps`，把对方**提交前那次依赖检查**提前跑掉 ——
  它要拉 ComfyUI 的 `/object_info`（约 9MB / 2s，对方缓存 5 分钟），提交前的检查走同一份缓存。
  跨域这条路对方页面常常从没打开过，不预热的话"第一次发图"就干等这 2s（失败静默；适配器内 2 分钟节流，
  输出一变会再热一次，因为写提示词的时间可能超过它的 TTL）。
- **依赖边界**：不 import 对方代码、不读对方库文件，全部走 HTTP 路由；`drawSeed()` 的区间与
  「先写快照再建作业」的顺序是**复刻**（跨插件只能这样），注释里写明了来源与同步义务。
  代码在 `client/src/crosscall/`（接口 / anima-plus 适配器 / 注册表三层），加第二个下游只需在注册表加一行。

## 验证

```bash
pnpm --filter @comfyui-web/prompt-editor typecheck   # vue-tsc
pnpm --filter @comfyui-web/prompt-editor test:contract   # 契约（SSR）+ 交互（真 DOM）
pnpm verify                                          # 仓级：typecheck → isolation → smoke → build → tabs-sync → contract
node scripts/scale-bench.ts                          # 规模基准（不在 verify 里：造 14 万条数据、要几十秒）
```

两层测试各管一半：

| 脚本 | 手段 | 管什么 |
|---|---|---|
| `scripts/contract-test.ts` | 注入最小 document 桩 + SSR 真渲染产物 | 产物形状（tabs/routes/样式）、首屏结构、纯函数（切分/重切/输出/服务端收敛/草稿两段装配）、词库（命中/别名/迁移/排序/导入不覆盖手改的）、**机翻表解析与导入**（引号里的逗号 / 占位行 / 同键去重 / lfs 指针 + 子进程真跑一遍脚本端到端）、非安全上下文下的降级 |
| `scripts/interaction-test.ts` | happy-dom 造 DOM，挂载产物、发真事件，**并记录发出去的请求** | 敲字/**失焦提交**、**输入法组字**、区块风格开关、单击改名、译文格编辑、双击禁用 → 输出跟着变；以及草稿的**两个写事件**（只发该发的那一段） |

交互层是补上 SSR 够不到的那一半：SSR 不跑事件处理器，"敲字进不去""点开关没反应"它一个都抓不到；
而草稿的"只发该发的那一段"更是只能从**请求**上看出来（DOM 上看不出），所以那一层顺便记录 fetch。

## 部署在局域网 http 上（非安全上下文）

浏览器只在**安全上下文**（https / localhost）里提供 `crypto.randomUUID`、`crypto.subtle`、
`navigator.clipboard`；本插件经常就是 `http://10.x.x.x:port` 打开的，所以这两处都做了降级：

| 用途 | 降级 |
|---|---|
| 条目 / 区块 id | `crypto.getRandomValues()`（**不**受安全上下文限制）自己拼 v4 UUID；连它都没有才退回 `Math.random` —— `client/src/model.ts` 的 `newId()` |
| 复制输出 | `navigator.clipboard` 不存在时退化到临时 `<textarea>` + `execCommand('copy')` |

契约测试两条都覆盖：`scripts/contract-test.ts` 会临时摘掉 `globalThis.crypto` 再 SSR 一次首屏
（线上踩过：局域网 http 下首屏直接抛 `crypto.randomUUID is not a function`，整个 tab 白掉）。

> 下一步接翻译时注意同一条：浏览器直连外部 API 时别用 `crypto.subtle` 做签名/加密，那条路在 http 下不存在。

## 词库往后怎么长

- **导入外部机翻表**：两条路都能用（见 [导入词库](#导入词库内置表--外部-csv)）—— 面板那个
  「导入内置机翻表」按钮读的是**产物自带**的 `assets/danbooru-zh.csv`（git-lfs，5.2MB / 14 万行，
  实测 64MB 库 / 2.1s），命令行那条吃任意 CSV。一次全量 + 以后靠 `hot` 排序把长尾压下去，
  比"先砍到 3 万"更划算（砍了再想加回来就得重新导一次；留全量随时能按 `hot` 一条 SQL 砍）。
- **内置一批常用 tag**：按 `post_count` 从 Danbooru 官方 API 拉 top N（实测 `limit=1000` 可用），
  顺手拉官方 `tag_aliases` / `tag_implications`（零维护），中文自己标或机翻。
- **规模**：词库**已经换成 SQLite**（`tags.db`）。下面量的是**发货的那套代码**
  （`node scripts/scale-bench.ts`，本机 Node 26，中位数）：

  | 词条数 | tags.db | 批量入库 | 改一条 | 面板(写后首次) | 面板(连续输入) | 搜索(英文) | 搜索(中文 2 字) |
  |---|---|---|---|---|---|---|---|
  | 1 000 | 0.5 MB | 15ms | 0.07ms | 1.8ms | 1.4ms | 1.4ms | 0.9ms |
  | 5 000 | 2.2 MB | 66ms | 0.05ms | 2.3ms | 2.0ms | 1.4ms | 1.8ms |
  | 20 000 | 8.9 MB | 316ms | 0.04ms | 6.1ms | 1.4ms | 1.5ms | 1.8ms |
  | 100 000 | 45 MB | 1.5s | 0.04ms | 22ms | 2.3ms | 2.6ms | 2.1ms |
  | 140 000 | 64 MB | 2.1s | 0.04ms | 32ms | 2.3ms | 2.4ms | 2.6ms |

  同一批数据在换库前的整文件 JSON 上（脚本里留作对照）：14 万条载入 223ms、
  **改一条 422ms**（全量 `stringify` + 原子替换）、面板查询 451ms。翻译命中两边都是 O(1)
  （SQLite 0.016ms/次）。**写路径的差别才是关键**：宿主是单进程单事件循环，同步 IO 卡的
  不只是这个 tab，是整个外壳和其它插件的请求 —— 422ms/次 vs 0.04ms/次。
- 「面板(写后首次)」比「连续输入」贵一档：全局计数（共 N 条 / 未分类 / 分类树）在写操作后要重算
  一遍（14 万条 26ms）。它跟搜索条件无关，所以缓存住（靠 `PRAGMA data_version` 感知别的进程写入，
  导入脚本灌完不用重启宿主）；连续输入时只剩列表那一条查询。
- **一次搜索的代价**（14 万条，单独量过）：命中一堆的 **0.5ms**（列表凑够一页就收 +
  总数封顶在 `limit+1`）；**一条都不命中的 50~70ms** —— 那是一次完整全表扫，救不了：
  给 `search` 建覆盖索引 `EXPLAIN QUERY PLAN` 照样是 `SCAN t`（实测没用，白搭 10MB 和写放大），
  加大页缓存也只有一成上下的差别。防抖窗口内够用。
- 磁盘 14 万条 64MB：**不上 FTS5**，所以没有 trigram 索引那多出来的 ~50MB。
  `PRAGMA temp_store = MEMORY` 是**必须**的：本环境 `/var/tmp` 存在但不可写，SQLite 挑临时目录
  会落到它头上，数据一大、排序/分组一溢出到磁盘就是 `SQLITE_CANTOPEN`（14 万条时必现）。
  它也是**每连接**的 —— 用别的连接去建索引/跑大查询也得自己设一遍。
- 官方只给英文（`name/category/post_count`），**中文必须自己攒** —— 这也是它唯一贵的地方。

价值不在"能查词"，在于**词库命中 = 零请求** —— 体验版约 6 次/窗口的限流下，
这才是让一整块提示词秒出译文的唯一办法。

## 构建

```bash
pnpm --filter @comfyui-web/prompt-editor build          # 或 pnpm build:plugins
pnpm --filter @comfyui-web/prompt-editor build:server   # 只打后端，改 server/ 时更快
pnpm --filter @comfyui-web/prompt-editor typecheck      # vue-tsc，含 server/**
```

服务端源码分成 14 个 `server/*.ts`（每个 ≤300 行），`scripts/build-server.mjs` 用 esbuild 打成**一个** `server.js`
（重挂只给入口加 `?v=`，多文件会命中 Node 的 ESM 缓存，见 `plugins/README.md` §2.4）；`tsconfig.json` 的
`include` 含 `server/**/*.ts`，所以 typecheck 连服务端一起查。产物写进 `tabs/prompt-editor/`，设置页点一次「重新扫描插件目录」即可装载。
