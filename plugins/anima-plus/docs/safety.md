# 硬件安全护栏

> 本文是 `plugins/anima-plus` 的**设计记录**（写得比代码早）。真相源是代码：`server/safety/`（`limits.ts` 常量与规则表 · `scan.ts` 扫描/夹紧 · `hits.ts` 命中形状 · `describe.ts` 描述与出口断言 · `effective.ts` 生效边界 · `quota.ts` 配额）；数值不一致时以代码为准。

> 目标读者：维护这个服务的自己。
> 背景：这套轻前端**要给其他人用**（`10.2.3.14:5180`），而 ComfyUI 那台机器只有一块卡。
> 一个 4096×4096 或 500 步的请求就能把显存/时间吃干净，把服务对所有人打挂。
>
> 结论先写在这里：**前端能改的东西一律不算防线**。
> 别人 curl 一下就能绕过表单，所以上限必须由服务端自己兜住，且在
> 「值已经落图」和「即将离开进程」这两个位置上各兜一次。

---

## 1. 威胁模型

| 来路 | 例子 | 能否被绕过 | 靠谁兜 |
|------|------|-----------|--------|
| 表单输入 | 步数填 500、宽填 4096 | 前端 `min/max` 只是 HTML 提示，改请求体即绕过 | 服务端（第 1、2 层） |
| 预设 | 旧预设里存着 2048×2048 | 预设是用户可写的服务器数据 | 服务端（第 1、2 层） |
| 工作流自身 | 从 ComfyUI 导出的图自带 4096 宽、默认 200 步 | 工作流是运维自己维护的，但**会犯错** | 服务端（第 2、3 层） |
| transform / const | 以后新加的变换器写错 | 同上 | 服务端（第 2、3 层） |
| 未来的新入口（批量、队列、API key） | 忘了接护栏 | — | 第 3 层（出口断言） |

不在本期范围：网络层限流/鉴权、磁盘配额、队列深度。见 §8。

## 2. 三道闸门

规范位置：`plugins/anima-plus/server/safety/`（`limits.ts` 规则表 · `scan.ts` 扫描/夹紧 · `describe.ts` 出口断言 · `effective.ts` 生效边界）。
这段代码是从已删除的 `apps/server/src/safety/limits.ts` **逐字**搬过来的，规则一条没动。

```
表单值 ──① coerceValues ──┐
                          ├─ 工作流 bindings 落图 ─→ graph
workflow.json ────────────┘                          │
                                                     ▼
                                    ② guardGraph（renderTemplate 收口）
                                       能追溯到用户 → 抛 422
                                       只来自工作流 → 夹紧 + WARN
                                       判定不了     → 抛 422（fail closed）
                                                     │
                                                     ▼
                                    ③ assertGraphSafe（ComfyClient.submit）
                                       纯断言、不改图，有一处越界就拒绝提交
```

### ① 表单值：`coerceValues`

按「表单 `ui.min/max` ∩ 安全策略」校验，越界即 422：

```json
{
  "error": {
    "code": "TEMPLATE_VALIDATION_FAILED",
    "message": "表单值校验失败：步数：不能大于 24（服务端安全限制）",
    "details": [{ "path": "values.steps", "message": "步数：不能大于 24（服务端安全限制）" }]
  }
}
```

> 说明：`details` 是给程序看的，前端目前只展示 `message`，
> 所以 `message` 里拼上了字段名 —— 否则用户只会看到一句"表单值校验失败"。

### ② 渲染结果：`guardGraph`

这是**唯一**能保证"值已经全部落图"的位置（表单 → binding → transform → graph），
所以复检放在这里：

- 越界值能追溯到用户填的字段 → **拒绝**。
  不悄悄改成安全值 —— 用户以为跑了 200 步、实际跑了 24 步，比报错更糟。
- 越界值只来自工作流（`const` 或导出的原值）→ **夹紧 + WARN**，
  工作流作者的笔误不该让服务对所有人不可用。
- 取值**判定不了** → **拒绝**（fail closed）。不猜就不会漏。

### ③ 出口：`assertGraphSafe`

`RealComfyClient.submit` / `MockComfyClient.submit` 的第一行就是出口断言：
不修改图，只扫描，有任何一处越界或无法判定就抛错。
**绝不把不确定的图发出去。**
走到这一步还越界，说明前面有 bug —— 宁可这次提交失败。

## 3. 规则表

```ts
export const MAX_STEPS = 24;   // 采样步数上限
export const MAX_SIDE  = 1216; // 图像单边上限
export const MIN_SIDE  = 64;   // 图像单边下限
export const MAX_LORAS = 8;    // LoRA 堆叠数量上限
export const MAX_BATCH = 1;    // 批量张数上限
```

> 这些上限是 **anima-plus 自己**的：核不管业务逻辑，**每个插件各定各的**。同样是边长 1216，
> anima-example 的步数上限放宽到 32 —— 它直接跑原生工作流；而这边是多 LoRA 叠加的系统，
> 配套 Turbo 工作流 6 步就能出图，步数窗口本该更窄。

### 3.1 数值规则（越界可夹紧）

| id | 字段（小写精确匹配） | 范围 | 豁免 | 理由 |
|----|--------------------|------|------|------|
| `steps` | `steps` | 1 – 24 | — | 步数线性拉长耗时 |
| `steps_to_run` | `steps_to_run` | 1 – 24 | `-1` | `-1` 是"跑满 steps"的哨兵，不是真的跑 -1 步 |
| `size` | `width`、`height`、`target_width`、`target_height` | 64 – 1216 | — | 生成/缩放的单边像素 |
| `batch` | `batch_size` | 1 – 1 | — | 显存随张数**线性**增长，1 张就是 1 张 |

### 3.2 数量规则（超量一律拒绝，不截断）

| id | 字段 | 上限 | 值形态 |
|----|------|------|--------|
| `loras` | `lora_str`、`temp_lora_str` | 8 | JSON 数组字符串 |

- 只盯 `lora_str` / `temp_lora_str`（LoRA 数组的**源头**）。
  `43.inputs.positive` 里的 `<wlr:>` 标签是同一次变换派生的、且会过滤 `hidden`，
  数量不会更多；`19.inputs.positive` 是主提示词，**不能**按这个规则数。
- **不夹紧**：截断 LoRA 堆等于悄悄丢掉用户选的 LoRA，图不对还查不出原因，
  不如直接报错（这也是它和数值规则分开的原因）。
- 空串 `""` 按 0 个算（ComfyUI 有时把空 LoRA 堆导出成空串）；
  不是合法 JSON 数组则算"判定失败"，照样拒绝。

三个设计取舍：

1. **按字段名匹配，不按绑定**。工作流换了，只要字段还叫 `width`，
   照样被管住。代价是字段名撞车（某个节点的 `height` 不是像素）会误夹 ——
   目前图里只有 `EmptyLatentImage` 有宽高，可以接受。
2. **`steps` 与 `steps_to_run` 分成两条规则**。`-1` 只对后者是合法的哨兵；
   合在一起会让 `steps=-1` 从 `exempt` 溜过去。
3. **数值 vs 数量两套规则**。数值可以安全地"夹小"；数量夹小等于改语义，只能拒。

### 加一条规则

```ts
// limits.ts
export const DEFAULT_LIMITS: readonly NumericLimit[] = [
  // ...
  { id: 'frames', label: '帧数', fields: ['frame_count'], min: 1, max: 24, integer: true },
];
export const DEFAULT_COUNT_LIMITS: readonly CountLimit[] = [
  // ...
  { id: 'controlnets', label: 'ControlNet 数量', fields: ['cn_str'], max: 2, format: 'json-array' },
];
```

改完即生效：表单边界、渲染复检、出口断言、`GET /api/template` 的
`ui.min/max` 全部跟着变，**不需要动任何工作流文件**。
若要在启动期就拦住越界，表单里的 `default` 会被同一条规则校验（见 §5）。

## 4. 取值解析：顺着连线找

ComfyUI 导出图里，`steps` 经常不是字面量，而是 `["49", 0]`（连到 `INTConstant`
的 `value`）。只看字面量会**整个漏掉**这类图。

本插件的工作流现在把 `steps`/`cfg`/`seed` 直接写在采样器上
（`26.inputs.steps = 20`），所以主路径是"字面量直接命中"；但**别人导出的图**仍然可能是
常量节点接线形状，`resolveNumeric()` 因此保留顺连线往上解析的能力，规则是：

| 上游节点情况 | 处理 |
|-------------|------|
| 只有一个数值输入 | 采用它（`26.inputs.steps → 49.inputs.value`） |
| 没有数值输入、只有一条连线 | 继续往上（最多 4 层） |
| **有多个数值输入** | **判定失败** → fail closed |
| 指向不存在的节点 / 不是数字也不是连线 | 判定失败 |
| 字符串形式的数字（`"6"`） | 判定失败（ComfyUI 也许能吞，护栏不靠猜） |

"判定失败"不会静默放过：渲染时抛 422，启动时直接让工作流加载失败（§5）。

## 5. 单一真相源：表单里的 `ui.max` 不是真相

`assets/form.json` 里 `steps.ui.max` 还是 200、`width.ui.max` 还是 4096 —— **故意不改**。
它们只是"这个工作流本身能跑多大"的描述；真正的安全包线属于**部署**，写在规则表里。

服务端在出口统一收窄，谁也不用手工同步：

- `GET /api/template` → `narrowTemplateBounds()`
  （实测下发 `steps.max = 24`、`width.max = 1216`，前端滑块因此不会给出"填了必被拒"的区间）
- `coerceValues` → `effectiveBounds()`（`ui.min/max` ∩ 策略，谁严格听谁的）

`effectiveBounds` 需要把 input 和规则对上。绑定直接写在被管控的字段上时
（`26.inputs.steps ← steps`）一步命中；仍然是常量节点接线形状的图，就**顺着连线往下游追**
（`49.inputs.value` → 下游的 `26.inputs.steps`）。`rulesOfTarget()` 做这件事（最多 3 层）。

### 启动期校验（`validateTemplate`）

| 情况 | 处理 |
|------|------|
| 工作流 `default` 越界 | **启动失败**（这种工作流一提交必被拒，是作者笔误） |
| 图里被管控字段**判定不了** | **启动失败**（等于"不知道会不会打爆显存"） |
| 图上**数量**超限（例如写死 9 个 LoRA） | **启动失败**（数量不夹紧） |
| 图里被管控字段带越界**数值** | **WARN 日志**，提交时夹紧 |

## 6. 已验证（本机真实服务 `10.2.3.22:8188`）

| 用例 | 结果 |
|------|------|
| `steps: 200` | 422 `步数：不能大于 24（服务端安全限制）` |
| `steps: 0` / `steps: -1` | 422 `不能小于 1` |
| `steps: 6.5` | 422 `采样步数 必须是整数，收到 6.5（26.inputs.steps）` |
| `seed: -1` | 放行，渲染时抽一个具体种子（0 ~ 2^53-1） |
| `seed: -5` / `seed: 1e20` | 422 `不能小于 -1` / `不能大于 9007199254740991` |
| `width: 4096` / `height: 1217` | 422 `不能大于 1216` |
| `width: 8` | 422 `不能小于 64` |
| `loras:` 9 条 | 422 `LoRA：最多 8 个（服务端安全限制），收到 9 个` |
| `loras:` 8 条 | 放行（边界含等号） |
| 请求体 300 KB | 413 `请求体过大（上限 256 KB）` |
| `steps: 24`、`1216×1216` | 放行（边界值含等号） |
| `width: 1000`（非 8 倍数） | 放行 —— 护栏只管硬件，不管画质 |
| 合法请求（默认 6 步 / 832×1216） | 真实出图成功（护栏零副作用） |
| 绕过渲染层直接 `client.submit(越界图)` | 被出口断言拦住（mock 与 real 都加了） |
| 并发提交超过队列深度 | 多出来的返回 429 `QUEUE_FULL`，占位不残留 |

自动化覆盖在 `plugins/anima-plus/scripts/smoke.ts`：**显存护栏**一节 11 项断言
（越界拒绝、guardGraph 夹紧、数量超限、取值不明 fail closed、正常图能过出口断言）
+ **配额** 3 项。旧服务那份 45 条断言的 smoke 随 `apps/server` 一起删除了，
新自检是纯函数级、不需要 ComfyUI 就能跑：`pnpm --filter @comfyui-web/anima-plus smoke`。

## 7. 不做的事（明确的取舍）

- **不静默改用户的参数**。用户的输入越界就报错，不用"我帮你调小"糊过去。
- **不把上限写进前端**。前端只拿到收窄后的 `ui.max`，改不了策略。
- **不追求"能跑就行"**。判定不了取值时选拒绝，不选尝试。
- **不做图生图**。因此请求体上限可以直接收到 256 KB，而不是为将来的上传留 32 MB。

## 8. 资源配额（`safety/quota.ts`）

`limits.ts` 管"图里的值"，`quota.ts` 管"服务自身的资源"。
两者都是服务端说了算，前端只是提示。

| 常量 | 值 | 行为 |
|------|----|------|
| `MAX_QUEUE_DEPTH` | 5 | 在途（created/queued/running）超过就 **429**，不再往下排 |
| `MAX_JOBS_RETAINED` | 200 | 任务表超条数时**从最旧的开始丢**；在途任务永不丢 |
| `MAX_BODY_BYTES` | 256 KB | Fastify `bodyLimit`，超出 → 413 |

两个实现要点：

1. **先登记再校验**。`submit()` 里先把任务写进 Map（这段没有 `await`），
   再数在途数量 —— 否则并发提交会都数到同一个旧值，5 个人能同时挤进一个空位。
   校验不通过就把占位删掉，不留僵尸。
2. **淘汰只碰已终态的任务**。丢掉在途任务 = 它永远收不到终态事件，
   而且会一直占着队列名额。被淘汰的任务同时清掉 `promptToJob` 映射。
